# DEVELOPMENT ENVIRONMENT

This document exists because the environment this repository is being developed in **cannot build
Android apps**, and hiding that would make every status claim in this repository worthless.

## 1. What is unavailable here

| Tool / host | Status |
|---|---|
| `java`, `gradle`, Android SDK | Not preinstalled |
| `services.gradle.org` (Gradle distributions) | Blocked |
| `repo1.maven.org` / Maven Central | Blocked |
| `dl.google.com` (Google Maven) | Blocked |
| GitHub release assets (`release-assets.githubusercontent.com`) | Blocked |
| `github.com` API/codeload, `registry.npmjs.org`, `pypi.org` | **Available** |

Consequence: `./gradlew build` cannot resolve plugins or dependencies here, so the Android module
cannot be compiled in this environment.

## 2. What was bootstrapped to make verification possible

Rather than write untested code, a working JVM toolchain was assembled from the allowed hosts:

- **JRE 25** from the `jdk4py` wheel on PyPI (`pip install --target /tmp/pylibs jdk4py`).
  It is a runtime only (no `javac`) but includes `lib/jrt-fs.jar`, sufficient to run a compiler.
- **Kotlin compiler 2.4.21** from the npm package `kotlin-compiler`
  (`npm install kotlin-compiler@2.4.21`) — the full distribution including `bin/kotlinc` and
  `lib/kotlin-stdlib.jar`.

The result is a genuine Kotlin compiler and JVM; `tools/jvm-verify/verify.sh` uses them.

## 3. Reproducing the verification run

```bash
export JAVA_HOME=/path/to/jre
export PATH="$JAVA_HOME/bin:/path/to/kotlin-compiler/bin:$PATH"
./tools/jvm-verify/verify.sh        # exits 0 only if every test passes
```

Expected tail:

```
Tests run: 120, Passed: 120, Failed: 0, Skipped: 0
VERDICT: PASS
```

## 4. Why there is a shim in `tools/jvm-verify/shim`

JUnit 4 cannot be downloaded here. The shim provides the subset of `org.junit`
(`@Test`, `@Before`, `@After`, `@Ignore`, `Assert`) and `kotlinx.coroutines`
(`runBlocking`, `withTimeoutOrNull`, `delay`, `async`) that the tests use, **with JUnit 4's exact
signatures** (message-first assertions), plus a small reflective runner.

Rules that keep this honest:

- Tests may only use symbols that also exist in real JUnit 4 — no shim-only helpers in test code.
- The shim never weakens an assertion; its `Assert` fails exactly where JUnit's would.
- Gradle builds use the real JUnit; the shim is only for the offline harness.
- Coroutine concurrency is **not** validated by the shim (everything runs inline), so no test
  makes a concurrency claim.

## 5. The real build (CI or a normal workstation)

```bash
# Requirements: JDK 17, Android SDK with platform 35 + build-tools 35.0.0, internet access.
./gradlew verify              # :core:test, :app:testDebugUnitTest, :app:lintDebug
./gradlew :app:assembleDebug  # produces app/build/outputs/apk/debug/*.apk
```

CI: `.github/workflows/verify.yml` (`domain-tests`, `android`, `release-guards`).

### About `gradlew`

The binary `gradle-wrapper.jar` is generated by `gradle wrapper` and cannot be produced here.
`gradlew` is therefore a POSIX launcher that runs the pinned Gradle version from
`gradle/wrapper/gradle-wrapper.properties`, using an installed Gradle of that version or downloading
it. On any machine with Gradle installed, replace it with the canonical wrapper:

```bash
gradle wrapper --gradle-version 8.9
```

## 6. What this environment still cannot verify

Even with the harness, the following require a real toolchain and a real device and are **not**
claimed anywhere in this repository:

- Compose compilation, rendering, screenshot/UI tests.
- Instrumentation tests, permission flows, background execution.
- Any inference, latency, RAM, thermal or battery measurement.
- Play Store policy compliance.
